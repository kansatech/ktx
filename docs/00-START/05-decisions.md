# Host Core Architecture Decisions

## One public SSH entry point

SSHPiper owns public TCP 22. Username `ktx` routes to the host's loopback-only OpenSSH service; workload usernames route to their assigned private targets. This keeps the operator command simple (`ssh ktx@host`) and makes username routing universal.

The tradeoff is that SSHPiper is now in the host administration path. Provider console/recovery access therefore remains part of the KTX recovery model.

## No root SSH

Root is never an SSH login. `ktx` is the human administrator and uses sudo. During initial bootstrap, password SSH is temporarily enabled only for `ktx` long enough to install a public key. The final public SSHPiper path is key-only.

## Preserve the SSH host identity

During the port-22 cutover, KTX copies the native OpenSSH Ed25519 host key to SSHPiper. The client therefore sees the same host key before and after the proxy takes over port 22.

## Native ingress, containerized workloads

Traefik, SSHPiper, OpenSSH, rsyslog, Docker, firewalling, and Host Core tools are native. Hosted applications belong in independent KTX module repositories.

## No Docker API dependency for ingress

Traefik uses watched dynamic files generated by KTX tools. SSHPiper uses explicit route directories. Neither needs the Docker socket.

## Deterministic private workload networks

Each workload instance gets a small deterministic bridge subnet and primary private address from Host Core. Native ingress targets those stable private addresses.
